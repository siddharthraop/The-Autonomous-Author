Abstract

Code and docs each run a DevOps loop: plan, build, test, release, deploy, operate and monitor. With docs as code, the docs loop runs on the same Git, CI and release tooling as the code loop2. At Google the two loops turn in the same sprint, and features do not ship without docs. One arc is different. Engineers write code with AI help, and more than a quarter of all new code at Google is generated by AI3. Writers still draft every docs change by hand. That one manual arc sets the pace of the whole docs loop.

The Autonomous Author automates that one arc. When a code pull request merges, it reads the change and the linked doc ticket, finds the affected pages and opens a first-draft docs pull request within minutes. Gemini writes the draft. Fixed Python checks test every sentence against its source, the style guide and the build. The writer reviews and approves the draft, as in the DDLC today. The agent cannot merge. The same checks then run on every docs pull request, and docs publish on the code release tag.

Every draft carries an explainability report with a confidence score from 1 to 10 and the source of every new sentence. The checks compute the score, not the model. Every run is logged, so a drift check can see when confidence falls or writers start to rewrite more.

§1 Client Brief

Google publishes documentation for its data center networking products, including Cloud NAT (network address translation). This MVP uses one Cloud NAT page as its sample: Tune NAT configuration, which lists the NAT timeouts, their defaults and the gcloud flags that change them4. The docs are in MyST Markdown in Git, the format that MANIFEST, the first project in this series, migrates DITA to5.

The team already runs docs as code. Its documentation development lifecycle (DDLC) is a DevOps loop of its own, and it turns in the same sprint as the code loop of the software development lifecycle (SDLC). Figure 1 shows the two loops. Writers are part of each sprint. The doc kickoff for an epic sets the doc type, audience and pages in scope, a Jira doc ticket tracks the docs, and docs publish with the release.

One contrast shapes the design. In the code loop, tests check the code against its specification. In the docs loop, the most useful test checks the docs against the code. The Autonomous Author adds that test (§5.3, tool 5).

The page is a good test for three reasons. A small code change, such as a new default value, changes several places on the page. The values are exact numbers and flag names, so a wrong draft is easy to detect. And the published page is a real reference answer: the MVP can replay a past change and compare its draft with what Google published.

§2 Problem Statement

The docs loop works. The pressure on it is pace. The 2025 DORA report found that 90% of software development professionals now use AI, and it linked AI adoption with higher software delivery throughput7. At Google, more than a quarter of all new code is generated by AI and reviewed by engineers3. When the code loop turns faster, more changes merge in each sprint, and each one needs a docs draft from the same writers.

Keeping up has a measured value. DORA found that documentation quality strengthens the effect of technical practices on organisational performance8. Figure 2 shows how large that effect is.

Figure 2

Source: DORA, documentation quality capability, 2022 research8. For every capability, teams with above-average documentation got a much larger lift. Docs that fall behind the code lose this effect.
2.1 Where the docs loop slows

Build, test, release and deploy already scale through pull requests and CI. Write does not. For each merged change, the writer notices it, reads the diff, finds every page that states the old behaviour and writes the update (Figure 3).

Problem statement
The Google data center documentation team runs its docs as a DevOps loop in step with the code loop. Every stage of that loop runs on shared tooling except Write: for every merged change, a writer reads the diff, finds the affected pages and writes the update by hand. As AI makes engineers faster, more changes merge in each sprint, and the Write arc sets the pace of the whole docs loop. AI drafting tools can help, but their output has no source for each fact, so writers must check everything again.

§4 User Stories

Each story comes from the Goal and Success fields in §3. The acceptance criteria are what the checks in §5 test.

US-01 · Docs Engineering Manager
As the Docs Engineering Manager, I want a scored draft for every merged change, so that the draft stage of the DDLC keeps pace with the merges in each sprint.
Accepted when: every merged pull request with a reader-visible change produces a docs pull request or a "no docs change" note · each one has a confidence score and is linked on its Jira doc ticket · no draft merges without a writer's approval.
US-02 · Senior Technical Writer
As a senior technical writer, I want each new sentence linked to its source, a confidence score and each unknown fact marked, so that I review facts instead of searching for them.
Accepted when: every new sentence has a source in the report · every literal value in a sentence appears in that source · facts with no source are [NEEDS INPUT] placeholders, never invented text.
US-03 · Docs Platform Engineer
As the docs platform engineer, I want every run logged and compared with a baseline, so that I see a fall in quality before writers complain.
Accepted when: every run writes one row to the run log · the daily drift check opens an issue when a threshold in §5.6 is crossed · the issue names the runs and what changed.
US-04 · Software Engineer
As a software engineer, I want the agent to ask me only what it cannot find in my change, so that I answer once and move on.
Accepted when: each placeholder becomes one question to the change author in the docs pull request · the change author is not asked about facts that are in the diff.
US-05 · Technical Support Engineer
As a support engineer, I want every page that states the old value found and updated, so that no page contradicts the product.
Accepted when: the stale value scan finds no copy of a replaced value in the affected pages · the draft builds and every link resolves · docs publish on the same release tag as the code.
US-06 · Amara (reader)
As a network engineer, I want the timeouts table to show the current default and the rule behind it, so that I configure a new gateway correctly.
Accepted when: every change item appears in the draft · the default value comes from the change or from a person, not from the model.
US-07 · Kenji (reader)
As a site reliability engineer, I want the page to tell me how to check the value in effect, so that I can troubleshoot an older gateway.
Accepted when: a new output field in the change produces a documented step · the command and field name match the change exactly.

§5 Proposed Design

The Autonomous Author does one thing. It turns a merged code change into a first-draft docs pull request, with a score and a report, for a writer to review. It is an agent built with Agent Development Kit (ADK), Google's open-source agent framework. ADK is licensed under Apache 2.0 and its agents can run on Cloud Run9. Gemini 3.8 Flash (gemini-3.8-flash, a stable model10) runs the agent and calls its tools through Gemini function calling11.

The agent has seven plain Python tools that give the same result every time, and one model step that writes and revises the draft. Its three check tools also run as a required check on every docs pull request, so the docs loop tests the writer's edits as well as the agent's. The model decides which pages to edit and how to word the change. The checks decide whether a sentence is grounded and what the confidence score is. The agent cannot change a check result, and it cannot merge.

5.1 How it works

The docs loop keeps its stages, its ceremonies and its Jira doc ticket. The agent acts at three points on it (Figure 6). At Write, the code merge starts the draft. At Test, fixed checks test the docs against the code and compute a confidence score. At Monitor, the run log shows drift in draft quality. The writer's time moves from writing to review.

5.3 Agent tools

1 · Read the change read_change

Reads the merged pull request: the diff and the description. It reads the linked Jira doc ticket with the Jira Cloud REST API17, which gives the doc type, audience and pages in scope from the doc kickoff. Parsers extract each reader-visible change item: a changed default, a new flag, a new API field or enum value. Each item gets an ID (C1, C2 ...) and keeps its old and new value.

Output: change.json · a change with no reader-visible items ends the run with a "no docs change" note

2 · Find the affected pages find_pages

Searches the docs repository for each change item: the flag name, the field name and the old value. It also reads the MyST substitutions file, so a value that is stored once is changed once5. Returns each page, line and the change item it matches.

Output: pages.json · page, line, change item, match type

3 · Draft and revise (Gemini) model step

Gemini edits the affected pages in MyST Markdown, following the doc type of each page. For each new or changed sentence it returns a source map entry: the change item, issue or page line it used. When a fact has no source, it must write a [NEEDS INPUT: question] placeholder instead. On a failed check it revises only the sentences that failed.

Output: patch for the docs repository · source map · at most 2 revisions

4 · Check the style check_style

Runs Vale with the Google package, a Vale version of the Google developer documentation style guide licensed under CC BY 4.018. Checks only the changed lines, so old issues on a page do not block a new draft. Tools 4 to 6 also run in docs-checks.yml on every docs pull request (§5.2).

Output: errors and warnings per 1,000 words, with line and rule

5 · Check the grounding check_grounding

Runs four checks. Source: every new sentence has a source map entry, and the source exists. Literals: every number, unit, flag, field and command in the sentence appears in its source. Coverage: every change item appears in the draft. Stale values: no affected page still states an old value that the change replaced.

Output: pass or fail for each sentence and change item, with the reason

6 · Check the build check_build

Builds the changed pages with Sphinx and treats warnings as errors. Runs lychee over the result to check links19.

Output: build pass or fail · broken links

7 · Score and report write_report

Computes the confidence score from the check results (§5.5) and writes the explainability report with its sources. Opens the docs pull request, posts the report as a comment and adds each placeholder as a question to the change author. Posts the link and score on the Jira doc ticket and moves it to review. Writes one row to the run log.

Output: draft pull request · report comment · doc ticket update · run log row

8 · Learn from the review record_review

Runs when the writer merges or closes the docs pull request. Compares the draft with the merged text and records the edit ratio: the share of the draft that the writer changed. It also recomputes the confidence score on the merged text, so the run log holds the score of what readers see. Repeated writer edits, such as the same word replaced in three drafts, become a proposed Vale rule that a writer approves.

Output: edit ratio and final score in the run log · proposed style rules
5.4 Agent loop

The agent runs tools 1 and 2, then asks Gemini for a draft. Tools 4 to 6 check it. When a check fails, Gemini reads the failure and revises only the failed sentences, then the checks run again. After two failed revisions, the agent stops revising. It replaces each sentence that still fails grounding with a placeholder, so no unchecked fact reaches the writer.

The agent always opens the pull request. It is a draft pull request, and the docs repository's branch protection requires a writer's approval before merge13. The confidence score sets the label: ready for review, review closely or needs writer. When a revision fixes the same failure type more than once and a writer approves it, the fix becomes a fixed rule in the tools, so the model is called less over time.

5.5 Confidence score and explainability report

The confidence score tells the writer how much review a draft needs, on a scale of 1 to 10. The tools compute it from check results only. The model never scores its own work. The weights below are the MVP's starting values. The platform engineer tunes them from the edit ratio that tool 8 records, so that a higher score means fewer writer edits.

A score is only useful if the writer can see what it is based on. So the explainability report always names its sources. It has five parts: what changed (the change items), sources (the code pull request, the doc ticket, each page and the style package version, each with a link), what the agent edited and why, where each sentence came from (sentence, source and check result) and what to check (placeholders, style issues and any sentence that needed a revision). 5.6 Observability and drift detection

ADK sends traces of every model and tool call to Cloud Trace through OpenTelemetry20. On Cloud Run, the trace_to_cloud option in the agent's server code turns this on21. Traces answer "what happened in this run". The run log answers "is quality changing over time".

Each run writes one row to a BigQuery table: run ID, model ID, prompt version, Vale package version, change type, confidence score and its parts, revisions, placeholders, tokens and time. Tool 8 adds the edit ratio after review. Once a day, a Cloud Run job started by Cloud Scheduler compares the last 10 runs with a baseline of 20 approved runs. When a check crosses its threshold, the job opens a drift issue in the docs repository with the runs and the rows that changed.

Drift typeSignal in the run logMVP thresholdResponse
Quality driftMean confidence score of the last 10 runs1.0 below baselineDrift issue. Compare prompt and model versions of the runs.

Configuration changeModel ID, prompt version or Vale version differs from baselineAny differenceReplay the evaluation set before the new version goes live.
Input driftChange type not seen in the baseline, for example a new file typeAny new typeFlag in the report. Add a replay case for the new type.

The evaluation set is a list of past Cloud NAT changes with their published pages as reference answers, such as the TIME_WAIT change in §2.1. The replay runs with ADK's evaluation tools. It uses response_match_score for overlap with the reference, and hallucinations_v1, which labels each sentence as supported by its context or not22. The second one uses a model as judge, so it runs only in the replay, never as the gate on a live draft.
